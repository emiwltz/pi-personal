# 0001 — The base: pi, not Pi Durable

Status: accepted (2026-11-16). How messages are delivered and replies attributed is settled by [0003](0003-delivery.md); how the agent is kept alive by [0002](0002-keeper.md).

## Decision

Build the core on **pi** (the coding agent, `@earendil-works/pi-coding-agent`), running its own terminal UI inside a Herdr Core terminal. Pi-personal adds the durability pi does not have, in two small pieces it needs anyway:

- the **port** (plain files) gives no loss and no doubles at the boundary, with what was taken in recorded in pi's own session file;
- a **runner** in the agent's terminal brings pi back in place when it dies, with a restart limit and a safe mode for extensions that break loading.

Pi Durable, the durable harness from the same authors, stays the candidate to revisit when its API is declared stable or when it gets a terminal UI.

## How the two were compared

Two throwaway prototypes (not published) shared the same file port, command-line client, runner and fake OpenAI-compatible model, in an isolated Herdr Core (Herdr Core 0.1.18, Node 22, pi and Pi Durable 1.5.2, Linux aarch64).

| | pi | Pi Durable |
|---|---|---|
| Code inside the agent | a pi extension of about 60 lines | a whole terminal program of about 100 lines (line input, printing, status, extension loading, safe mode) around the library |
| Memory | 126 MB | 83 MB |
| Install size | 27 MB | 5 MB, plus its dependencies |

Both passed the same scenarios: a message from the command line; a message while the agent works; the same id twice; `kill -9` in the middle of a run; an extension broken at load; a person typing while port messages arrive; the agent blocked on a question. The differences:

- after `kill -9`, pi came back in 0.6 s but **abandoned the work that was cut off**; Pi Durable continued it by itself. (Pi-personal closes most of that gap: after a crash, the bridge asks the agent to continue, with one visible note.)
- an extension broken at load makes pi exit, naming it; Pi Durable's host skipped it without a restart;
- pi's terminal UI, status reporting (Herdr shows `agent: pi`), question dialogs and typed input all came for free; with Pi Durable each was ours to write, and a question waiting for a person lived only in memory.

What surprised us, and the design now relies on: text typed into pi while it works is queued by pi itself; pi's `ui_prompt_start` event carries the kind and text of a question, so the port can report "blocked" from inside pi; Herdr still sees pi when it runs as a child of the runner; pi writes its session file only once the conversation holds a user or assistant message.

## Why pi, criterion by criterion

1. **Stability of what we depend on.** pi 1.x is stable and widely used. Pi Durable says "Experimental. The API changes without notice between releases": its changelog listed 40 breaking changes over five releases. → pi.
2. **Visible and steerable in Herdr.** pi reports its status natively and has a full terminal UI that a person can take over (`/model`, `/login`, tool rendering, sessions). → pi, by far.
3. **Never losing or doubling; coming back after a crash.** Pi Durable gives this inside the harness. With pi, the port gives it at the boundary and the runner brings pi back; resuming cut-off work needs the note above. → Pi Durable is better; pi is sufficient.
4. **Reuse of the existing ecosystem.** pi loads packages, skills, prompt templates, MCP servers and `AGENTS.md`; Pi Durable reads nothing from disk. → pi.
5. **Code to own when the base changes.** pi: one extension on a documented, versioned API. Pi Durable: a terminal UI, status, extension loading, credentials and dialogs, on a moving API. → pi.
6. **Room for what comes next.** Pi Durable has durable timers built in; with pi, wake-ups come through the port, which keeps the core free of a scheduler. → a slight edge to Pi Durable.

## Rejected

- **Pi Durable as the base.** The best recovery, but we would own a terminal product on an experimental API, and lose pi's ecosystem.
- **A Pi Durable inbox in front of a pi session.** Two harnesses and two stores, and the guarantee would still end at pi's door, where the port already puts it.
- **pi in RPC mode under our own UI.** The same problem as Pi Durable: we would write the UI.

## Consequences

- Pi-personal pins its own copy of pi instead of using the user's, so an update elsewhere cannot break the bridge. The behaviours of pi and Herdr Core the core relies on are checked by `test/contracts.test.ts`.
- Herdr Core keeps programs running across its own crash or update, never reruns a program that ended, and keeps terminal names unique among live terminals: the runner and `up` exist because of the second fact, and "one session per agent" comes from the third.

## Cost of switching later

The port does not mention the base. Moving to Pi Durable would mean replacing the bridge and the runner's start command, and writing the terminal UI that Pi Durable lacks; the UI is the expensive part.
